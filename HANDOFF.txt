Project overview
----------------
This project is a FastAPI + Celery lead-generation pipeline. It scrapes Google
Maps with Playwright, stores campaigns/leads/reports/drafts in Firebase
Firestore, optionally analyzes leads with Gemini, optionally creates Gmail
drafts, optionally syncs records into Notion, and supports ZIP exports.

Primary runtime pieces:
- FastAPI app: app/main.py
- Campaign routes: app/routes/scrape.py
- Lead routes: app/routes/leads.py
- Report routes: app/routes/analyze.py
- Email draft routes: app/routes/email.py
- Export routes: app/routes/export.py
- Runtime config route: app/routes/config.py
- Celery tasks: app/workers/tasks.py
- Celery app: app/workers/celery_app.py
- Firebase helpers/collection names: app/firebase.py
- Google Maps scraper: app/services/maps_scraper.py
- Website scraper: app/services/website_scraper.py
- Gemini analyzer/email prompts: app/services/gemini_analyzer.py
- SerpAPI organic evidence service: app/services/serpapi_service.py
- Notion sync service: app/services/notion_service.py
- Tests: tests/test_campaign_helpers.py
- Frontend (React + Vite + react-query + sonner): frontend/src/
  Pages live in frontend/src/pages, shared UI in frontend/src/components,
  API client in frontend/src/lib/api.ts, job registry in frontend/src/lib/jobs.ts.

The user now wants to run the app inside WSL/Linux only. Avoid Windows-specific
startup logic. The local flow is:
1. Start Redis inside WSL/Linux:
   ./scripts/start-redis.sh
2. Start Celery worker:
   ./scripts/start-worker.sh
3. Start FastAPI/docs server:
   ./scripts/start-api.sh

Use http://127.0.0.1:8000/docs in the browser. Do not use http://0.0.0.0:8000/docs
in the browser; 0.0.0.0 is a bind address, not a browser destination.

Google Maps scraper work
------------------------
The original problem was that the Google Maps scraper returned too few results
and many cards failed extraction. We improved the scraper and campaign behavior:

- Maximum Maps scrape limit is now 500 by default.
- Campaign creation supports per-campaign max_results and dedupe_enabled.
- Google Maps scraper was hardened to reduce re-clicking and repeated card
  extraction problems.
- Maps metrics are stored on campaign status and include fields such as:
  businesses_persisted, global_duplicates_skipped, max_maps_results_used.
- Missing-website leads get a quality flag:
  {"missing_website": true/false}
- Scrape cancellation checks were added inside the scroll/extract loop.
- Existing no-website leads can be repaired in place with:
  POST /api/campaigns/{campaign_id}/repair-websites
  This revisits each lead's saved Google Maps URL, re-reads stabilized detail
  rows, and updates website/has_website/missing_website without creating
  duplicate leads.
- By default, repaired leads are reset to scrape_status=pending so later resume
  runs process them through the website track. Use
  ?reset_status=false to only update website fields.
- Global lead dedupe can be enabled/disabled.

Relevant files:
- app/services/maps_scraper.py
- app/workers/tasks.py
- app/schemas.py
- app/routes/scrape.py

AI processing toggle
--------------------
The user wanted to pause the AI part so scraper runs do not consume AI tokens.
The pipeline supports AI_PROCESSING_ENABLED. When false, full runs still process
has-website leads with deterministic website appraisal and Gmail drafts, but no
AI rewrite is used and no-website leads are left for the generated-website
publish workflow.

------------------
Notion sync is optional. The app syncs:
- Campaign
- Lead
- Report
- Outreach
- Search Evidence

Expected existing Notion databases:

- lead
- report
- outreach
- Search Evidence

All title property names are assumed to be "Name", based on user confirmation.

Configured relations the user created:

- Campaign: Lead
- Report: Lead, Outreach
- Outreach: Lead, Report

Environment values documented in .env.example include:
- NOTION_API_KEY
- NOTION_CAMPAIGNS_DB_ID
- NOTION_LEADS_DB_ID
- NOTION_REPORTS_DB_ID
- NOTION_OUTREACH_DB_ID
- NOTION_SEARCH_EVIDENCE_DB_ID
- NOTION_REQUEST_DELAY_SECONDS

Do not read .env to verify these. The runtime config endpoint safely shows
whether the DB ids are configured without exposing secrets.

Notion sync behavior:
- app/services/notion_service.py writes only properties that exist on the target
  database.
- It now also checks property types. If a property exists but has the wrong
  type, it logs a warning and skips that property instead of failing the whole
  page.
- Lead sync now supports both lead database URL column names: "Generated live
  url" and the older "Generated website url". It writes to whichever one exists
  in the target schema, and it can pull either alias back into Firestore as
  generated_website_url.
- Notion 400 responses are logged with the response body to reveal the exact
  rejected property.
- Transient Notion errors are retried.
- Sync request pacing is controlled by NOTION_REQUEST_DELAY_SECONDS, default
  0.35 seconds.

Backfill endpoint:
POST /api/campaigns/{campaign_id}/sync-notion

Default behavior now creates only missing Notion pages and skips records that
already have stored Notion page ids. This avoids re-patching every lead on every
backfill run.

Force behavior:
POST /api/campaigns/{campaign_id}/sync-notion?force=true

This updates existing Notion pages too, preserving the old repair/update-all
behavior.

Search Evidence Notion behavior:
- One Notion page per campaign query.
- Stored on campaign as search_evidence_notion_page_id.
- Top Results stores only the top three business-owned organic URLs after
  filtering out directories/social/forums/non-business sites.
- Raw JSON is no longer synced to Notion. The broader evidence payload remains
  in Firestore; Notion keeps only the human-checkable search summary fields.

If Search Evidence does not sync:
- Check logs/celery.log for Notion response body.
- A 404 on GET /databases usually means wrong DB id or database not shared with
  integration.
- A 400 on POST /pages usually means a property type mismatch. Current code now
  logs and skips mismatched properties where possible.

Generated website and outreach flow
-----------------------------------
The static website and outreach flow has been split into two lanes:

- `needs_website=true` is still the gate for website generation.
- `POST /api/campaigns/{campaign_id}/websites/build` only creates previews.
- `POST /api/campaigns/{campaign_id}/websites/publish` commits/pushes previews,
  then marks the leads as hosted and writes the live URL back to Firestore and
  Notion.
- When a lead already has a draft preview directory and is rebuilt, the old
  preview directory is deleted first so stale draft sites do not pile up.
- Website-lead audit outreach still comes from the existing website analysis
  path, but the prompt now includes browser-quality signals so the email is more
  business-goals focused.
- Generated-site outreach for no-website leads is now explicit and only happens
  when there is a hosted/generated live URL.
- New explicit outreach trigger:
  `POST /api/campaigns/{campaign_id}/outreach/drafts`
- Publish also triggers the generated-site outreach draft job so the email can
  reference the live generated site once hosting is complete.

SerpAPI / organic search evidence
---------------------------------
The app no longer uses Google Custom Search for this path. It uses SerpAPI.

Endpoint used by app:
https://serpapi.com/search.json

Params:
- engine=google
- q="{niche} in {location}"
- api_key=SERPAPI_API_KEY
- num=SERPAPI_RESULTS_LIMIT
- hl=en
- gl=us

Relevant env values in .env.example:
- SERPAPI_API_KEY
- SERPAPI_RESULTS_LIMIT=10
- SEARCH_EVIDENCE_STALE_AFTER_DAYS=30

Search evidence service:
- app/services/serpapi_service.py

Evidence payload includes:
- provider
- query
- normalized_query
- generated_at
- last_search_evidence_refreshed_at
- search_evidence_age_days
- organic_results
- business_results
- organic_results_count
- business_results_count
- has_useful_business_results
- cache_hit
- source

Business-owned filtering:
The app filters out domains such as Google, Yelp, Angi, Thumbtack, BBB,
YellowPages, Facebook, Instagram, LinkedIn, Reddit, Twitter, X, TikTok, YouTube,
MapQuest, TripAdvisor, Nextdoor, Wikipedia, Foursquare, Trustpilot, etc.

The filter uses improved root-domain normalization so subdomains of blocked
domains are also excluded.

Confidence scoring:
Business-owned organic results get confidence_score using signals including:
- not a blocked directory/social/forum domain
- organic result position
- niche relevance in title/snippet/domain
- location relevance in title/snippet/domain
- HTTPS URL

Only business-owned results with sufficient confidence are stored in
business_results.

Search evidence cache:
- Firestore collection: search_evidence_cache
- Cache key: normalized "{niche} in {location}"
- Repeated campaigns with the same normalized query can reuse cached evidence
  instead of calling SerpAPI again.

Source logging:
app/workers/tasks.py logs structured extra fields with event:
- search_evidence_resolved
- search_evidence_stale

source will be one of:
- campaign
- cache
- serpapi

This is useful in Celery logs to see whether a run reused campaign evidence,
reused shared cache, or called SerpAPI.

No-website appraisal path
-------------------------
Previous behavior scraped Google Maps again to find competitors and then scraped
competitor websites per no-website lead. The user questioned this as overhead,
and we replaced that flow.

Current no-website path:
- Uses campaign-level SerpAPI organic evidence.
- Calls SerpAPI once per campaign query context, then reuses it for all
  no-website leads.
- Does not scrape Google Maps again for competitors.
- Does not scrape competitor websites.
- Uses deterministic no-website appraisal and template-based email drafts from
  app/services/no_website_appraisal.py.
- Optional AI polish is controlled by OUTREACH_AI_REWRITE_ENABLED. When false,
  no-website outreach copy is fully template-based.

Relevant files:
- app/workers/tasks.py
- app/services/no_website_appraisal.py
- app/services/serpapi_service.py

Claim guardrails:
No-website appraisal now uses explicit allowed/disallowed claims derived from
evidence:
- Allowed: say business-owned websites appear in organic Google results for the
  checked query, when such results exist.
- Allowed: say a no-website business lacks an owned page that can rank
  organically or convert searchers.
- Not allowed: claim anything about Google Ads, Maps rankings, traffic volume,
  certain revenue, or website quality not supported by snippets.

Fallback behavior:
If no useful business-owned organic URLs remain after filtering, the AI should
avoid naming competitors and focus on the absence of an owned website that can
rank organically.

Exports
-------
Exports were moved to background jobs to avoid slow direct responses for large
campaigns.

Background export endpoints:
- POST /api/exports/campaigns
- GET /api/exports/{export_id}/status
- GET /api/exports/{export_id}/download

Exports are ZIP files. For all-campaign export, the ZIP contains one folder per
campaign, and each campaign folder contains CSV and JSON files with metadata.

Export file behavior:
- Exports are written temporarily under exports/.
- Export downloads are deleted after download.
- Undownloaded exports expire after EXPORT_RETENTION_HOURS, default 24.
- User-facing message says to download immediately.

Direct export:
- GET /api/campaigns/{campaign_id}/export.zip
- Limited by DIRECT_EXPORT_MAX_LEADS, default 100.
- If a campaign exceeds the limit, the endpoint aborts and the user should use
  the background export flow.

The direct all-campaign export endpoint was removed.

Tombstone-first delete flow (2026-09-25):
POST /campaigns/delete no longer just queues work. Order:
  1. Confirm token check (DELETE_CAMPAIGNS, unchanged: that is still the API
     contract even though the UI asks the user to type the campaign name).
  2. _tombstone_campaigns(ids): a Firestore TRANSACTION that re-reads the
     running/analyzing guard from the same snapshot it writes, then sets
     status=deleting + deleted_at + requeue_at (now + 10 min). 409 if any
     target is running/analyzing. This guard now also applies to scope=all
     (previously scope=all only got it inside the task).
  3. bulk_delete_campaigns.delay(ids) with the materialised id list. If
     enqueue throws, the tombstones stand: log it, return job_id="", and the
     reconcile task re-enqueues later.
Why: rows disappear from every read immediately (the UI refetches right
after queueing), the delete intent survives crashes, and the transaction
closes the start-vs-delete race.
Where tombstones are hidden:
- _list_campaign_docs filters status=deleting next to the pre-existing
  "archived" filter, BEFORE the status-filter logic, so ?status=deleting
  returns []. Every UI surface reads GET /api/campaigns (home funnel,
  campaigns list, exports picker, campaign dropdowns), so one filter covers
  them all.
- build_campaigns_zip_for_ids excludes deleting from all-campaigns exports.
- _ensure_campaign_can_run refuses status=deleting with 409 "Campaign is
  being deleted." so nothing can resurrect a tombstone by starting it.
Worker behaviour (unchanged code, now load-bearing):
- _delete_campaign_doc deletes children first and the campaign doc LAST, so
  a mid-purge failure leaves the tombstone in place (still hidden, retried).
- _bulk_campaign_action counts per-campaign failures instead of raising;
  failed campaigns keep status=deleting and get retried by reconciliation.
- task_acks_late=True (celery_app.py), so a worker crash redelivers the task.
Reconciliation (the cleanup guarantee):
- New task tasks.reconcile_deleting_campaigns (app/workers/tasks.py):
  queries status=deleting, picks docs whose requeue_at has passed
  (_stale_deleting_ids helper), stamps requeue_at +10 min, then re-enqueues
  bulk_delete_campaigns. The purge is idempotent, so duplicate enqueues are
  harmless. Covers: crash between tombstone and .delay(), broker outage,
  lost/expired task records, and failed purges.
- Driven by celery beat: beat_schedule in app/workers/celery_app.py runs it
  every 300s. scripts/start-worker.sh now starts beat alongside the worker
  (logs/celery-beat.log). RESTART THE WORKER after pulling this change,
  otherwise neither the new task nor beat is running.
- Beat schedule file celerybeat-schedule* is gitignored (backend/.gitignore).
Known limits:
- Direct URLs to a tombstoned campaign (GET /campaigns/{id}/status) still
  resolve until the purge lands; the lists never show it.
- GET /leads/{id} still resolves briefly for leads of a deleting campaign.
- If the worker is down for a long time, rows stay hidden until it returns.
  Per the user, cleanup correctness beats UI feedback here.

Known caveats and follow-ups
----------------------------
1. Search Evidence Notion "Top Results" is a text field containing URLs, not a
   relation to a separate results database. The user considered one-row-per-
   result auditing but did not choose it.

2. Search evidence cache is shared by normalized niche/location. This is
   intentional to save SerpAPI calls across repeated campaigns, but clearing the
   cache may be needed when a niche/location query should be refreshed globally.

3. GET /campaigns/{id}/search-evidence does not call SerpAPI. It only reads
   campaign-stored evidence.

4. POST /campaigns/{id}/search-evidence without force reuses campaign evidence
   or shared cache where possible.

5. POST /campaigns/{id}/search-evidence?force=true calls SerpAPI and overwrites
   stored campaign evidence and shared cache.

6. POST /campaigns/{id}/search-evidence?refresh_if_stale=true refreshes only if
   campaign/cache evidence is older than SEARCH_EVIDENCE_STALE_AFTER_DAYS.

7. Tests currently focus on helpers rather than full end-to-end API tests. Main
   test file: tests/test_campaign_helpers.py.

8. Some files contain pre-existing mojibake in prompt strings, such as encoded
   em dashes. Do not do broad formatting cleanup unless the user asks.

9. Do not revert or delete user_data/Default runtime files unless explicitly
   requested.

10. After code or env changes, restart both FastAPI and Celery. Celery will not
    pick up new code/env values until restarted.
